# Remediation playbooks

Most findings are fixed with a code change (SKILL.md step 9). Secrets and vulnerable dependencies aren't: deleting a leaked key doesn't make it safe, and a vulnerable library is often pulled in by another library you can't edit. Use these playbooks for them, and make each recommendation concrete for the repository's stack.

## Leaked secrets

A secret that has been committed is compromised. Anyone with a clone, fork, CI log, or backup of the repository has it, and removing it from the file or from history doesn't change that. The order matters:

1. **Revoke and rotate first.** Disable the exposed credential at its provider and issue a new one. Say which provider and credential type it is (for example "AWS access key for IAM user `deploy-bot`", "GitHub personal access token", "Postgres password for `orders-db`"). Rotation is the fix; everything after this is cleanup and prevention. Never rotate, revoke, or test the credential yourself (SKILL.md rules 4 and 5).
2. **Check whether it was used.** Recommend reviewing the provider's access logs (for example CloudTrail for AWS keys) for activity since the commit date. Give the date of the commit that introduced it.
3. **Move it out of the code.** Propose a diff that reads the value at runtime from the stack's normal mechanism:

   | Stack | Mechanism |
   |---|---|
   | AWS workloads (any language) | AWS Secrets Manager or SSM Parameter Store, through the SDK or the platform's injection (ECS secrets, Lambda environment from Secrets Manager); better still, an IAM role instead of a static key |
   | Kubernetes | External Secrets Operator or the Secrets Store CSI driver; avoid plain `Secret` manifests in git |
   | Spring Boot | `spring.config.import` from Secrets Manager or Vault; environment variables |
   | .NET | `IConfiguration` with Azure Key Vault or AWS providers; User Secrets for local development only |
   | Node, Python, Go, Rust | Environment variables injected by the platform; the cloud SDK's secrets client |
   | CI/CD | GitHub Actions or GitLab CI secrets and variables (masked, protected); OIDC federation to the cloud instead of stored keys |
   | Terraform / CDK | Reference Secrets Manager or SSM; mark variables `sensitive = true`; never put secrets in `.tfvars` committed to git |

4. **Optionally purge history.** Rewriting history (`git filter-repo`, or BFG Repo-Cleaner) removes the secret from future clones but not from existing ones. It also requires a force-push that every collaborator must handle. Recommend it only when the repository is or will become public, or when policy requires it. Don't run it; it's the user's decision and it rewrites shared history.
5. **Prevent recurrence.** Recommend a pre-commit secret scan (Gitleaks or Betterleaks as a pre-commit hook) and the platform's push protection (GitHub secret scanning push protection, GitLab secret push protection).

Report the secret finding with these steps as its fix, in this order, instead of a single diff.

## Vulnerable dependencies

For each vulnerable package:

1. **Find the minimum fixed version** from the advisory (OSV, GitHub Advisory Database, or the scanner's output). Never from memory (SKILL.md rule 9). If several advisories affect the package, take the lowest version that fixes all of them.
2. **Check the jump.** A patch or minor upgrade is usually safe. A major upgrade may break the build: say so, link the package's changelog or release notes, and name the breaking changes if the changelog is in the scanned data. Prefer the smallest upgrade that fixes the vulnerability.
3. **Direct dependency:** propose the version change in the manifest as a diff, and note that the lockfile must be regenerated by the package manager. That runs the install, so it needs approval (rule 3).
4. **Transitive dependency** (pulled in by another package): first check whether upgrading the *direct* dependency that pulls it in fixes it, because that's the cleanest fix. If not, force the version with the ecosystem's override mechanism:

   | Ecosystem | Force a transitive version |
   |---|---|
   | npm | `"overrides": { "vulnerable-pkg": "1.2.3" }` in `package.json` |
   | Yarn | `"resolutions": { "vulnerable-pkg": "1.2.3" }` |
   | pnpm | `"pnpm": { "overrides": { "vulnerable-pkg": "1.2.3" } }` |
   | Maven | `<dependencyManagement>` entry with the fixed version |
   | Gradle | `constraints { implementation("group:artifact:1.2.3") }` |
   | pip | Pin it in `requirements.txt`, or in a constraints file passed with `-c` |
   | Poetry, uv | Add it as an explicit dependency with the minimum fixed version |
   | NuGet | Add an explicit `<PackageReference>` at the fixed version (or a `PackageVersion` in Central Package Management) |
   | Go | `go get module@v1.2.3`, then `go mod tidy` |
   | Cargo | `cargo update -p crate --precise 1.2.3`; a `[patch]` section only as a last resort |

   An override can break the package that depends on it. Say so, and recommend running the tests.
5. **No fix available:** say so plainly. Then offer, in order:
   - Whether the vulnerable code is reachable. If it's not, record that with the evidence (govulncheck, OSV-Scanner call analysis, or traced code paths). A VEX statement is a standard way to record "not affected".
   - A compensating control for the specific attack: disable the vulnerable feature, add input validation in front of it, or isolate it.
   - Replacing the package with a maintained alternative.

   KEV-listed vulnerabilities with no fix are the top priority to mitigate.
6. **Container base images:** update the base image tag to a patched release, and pin it by digest. Consider a smaller base (distroless or a slim variant) to reduce the number of vulnerable packages.

Group dependency fixes by manifest. One upgrade often fixes several findings, so list which findings each change closes.

## Infrastructure as code

Propose the corrected resource or construct as a diff, and note what the change does to running infrastructure. For example: enabling encryption on an existing RDS instance requires a snapshot and restore, and changing a security group takes effect immediately. Recommend applying through the team's normal plan, review, and apply process. Never apply it yourself.
